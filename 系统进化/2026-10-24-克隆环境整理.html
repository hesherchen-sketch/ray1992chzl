3. 逐项真相（硬数据）

3.1 任务没丢，是全部暂停

  • 总量：cron/jobs.json 34 + profiles/canghai-review/cron/jobs.json 1 + profiles/canghai-plan/cron/jobs.json 1 + profiles/canghai-fetch/cron/jobs.json 1 = 37
  • 读取字段 enabled：37/37 = false（注意：paused_at/paused_reason 全部为 null，只看这两个字段会误判成”在跑”）
  • 任务定义文件位置：~/.hermes-canghai/cron/jobs.json（主库）+ ~/.hermes-canghai/profiles/<名字>/cron/jobs.json（三个角色库）
  • 执行历史库：~/.hermes-canghai/cron/executions.db

3.2 模型错配：不是 429，是 404

实测 hermes-canghai -m gpt-6.1-sol -z "..." 返回：

HTTP 404: The requested model does not support the agent plan feature.

gpt-6.1-sol 属于 openai-codex 通道，新 Ark key 上不存在该模型 id。这类错误重试永远不会成功，唯一修法是改 pin。

3.3 coding-plan 的 8 个任务带端点硬覆盖

8 个任务同时钉 provider=volcengine-coding-plan 和 base_url=https://ark.cn-beijing.volces.com/api/coding/v3。这是合法的”同族覆盖”（provider 与端点一致），但一旦把 provider 改成 agent-plan（正确端点是 /api/plan/v3）而 base_url 不动，就会变成 401 鉴权失败 —— 这是 2026-10-12 已经踩过一次的坑。

实测：hermes cron edit --provider 对本身没有 base_url 的任务不产生覆盖，对已有 base_url 的任务不会自动清除（单点试改的 dividend-picker 原本 base_url 为空，改完仍为空；8 个 coding 任务改完 base_url 原样保留）。因此单独做了原子写清理 + 回读。

3.4 profile 库里的任务不能用 default 库的命令改

hermes cron edit 没有 --profile 参数。跨库任务（E2 周度进化、P2 午盘修订、午盘快照）必须写成：

不带 -p 会报 Job not found。

3.5 hermes-visitors 删得掉

删前扫引用：cron/jobs.json 里唯一命中是「复盘推送」prompt 正文提了一句（deliver=local，不是投递目标）；gateway_state.json 里是网关服务注册（重启网关自动消失）。没有任何任务依赖它。

处理：mv profiles/hermes-visitors → cache/scratch/profile-retired-hermes-visitors-<时间戳>/（可逆，不是 rm）。

5. 根因

  1. 克隆把源机的”模型 pin”一起搬过来了。任务库里的 model/provider 是创建时 pin 死的，不跟随 profile 默认值。源机 10-21 切到 GPT 通道后，15 个任务就钉在那条通道上；克隆到新机、换了 Ark key，pin 值不变 → 404。
  2. 批量迁移脚本的目标是写死的。scripts/cron/switch_cron_provider.py 里 TARGET_PROVIDER = "volcengine-coding-plan"、TARGET_BASE_URL = ".../api/coding/v3"。这次目标是 agent-plan，直接跑脚本会把 8 个任务又改回 coding 档 —— 所以没有用它，改用官方 CLI 逐条改。
  3. 桌面端看不到任务，是因为网关/项目绑定与 profile 归属是两套东西。任务挂在 Hermes home 的 cron 库里，不挂在项目里；桌面左栏显示的是 Projects（工作区），不是任务列表。
